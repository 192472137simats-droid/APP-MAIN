# C++ core and standalone demo

The C++ server accepts text-layer PDF uploads, extracts text with Poppler, and
stores paper records in SQLite. Its own browser page in `cpp/web/` lets you
upload a PDF, browse the saved library, read extracted text, and download it as
`.txt`. You can also request a structured AI analysis of a saved paper. The
analysis runs in a background worker and its status and result are saved in
SQLite.

The original full application remains in Python. Run
[`scripts/run-integrated.ps1`](../scripts/run-integrated.ps1) from the repository
root to use the original multi-section interface and research features with the
C++ service handling structured paper analysis. The integrated app continues to
store papers and analysis in the original `data/researchadvisor.db` database.

## Build

Install a C++17 compiler, CMake, pkg-config, Poppler's C++ development library,
SQLite's development library, libcurl, and JsonCpp. On Windows, the MSYS2 UCRT64
packages are
`mingw-w64-ucrt-x86_64-toolchain`, `mingw-w64-ucrt-x86_64-cmake`,
`mingw-w64-ucrt-x86_64-ninja`, `mingw-w64-ucrt-x86_64-poppler`, and
`mingw-w64-ucrt-x86_64-sqlite3`, `mingw-w64-ucrt-x86_64-curl`, and
`mingw-w64-ucrt-x86_64-jsoncpp`.

From the repository root:

```sh
cmake -S cpp -B cpp/build
cmake --build cpp/build
./cpp/build/research-advisor-server 8080 cpp/web
```

On Windows the executable has a `.exe` suffix. Open
<http://127.0.0.1:8080/> after starting the server. It listens only on
`127.0.0.1`. By default, it creates `data/researchadvisor-cpp.db` relative to
the working directory. Set `RESEARCH_ADVISOR_DATA_DIR` to choose another data
directory.

## Model configuration

Set `LLM_API_KEY` and `LLM_MODEL` in the server environment or in a local
`.env` file in the working directory. `LLM_BASE_URL` is optional and defaults
to `https://openrouter.ai/api/v1`. The C++ server uses the same variable names
as the Python app. It accepts HTTPS providers or a loopback HTTP model server.
Never commit the `.env` file. The **Analyze paper** button sends the extracted
text to the configured provider, which may charge for requests.

The model receives at most 180,000 bytes of extracted text. The app asks for
JSON with summaries, findings, limitations, and research directions. It stores
the result or a retryable error in SQLite. Analysis is generated by a model and
needs checking against the paper; research directions have not yet been checked
against later literature.

## Available API

| Route | Purpose |
|---|---|
| `GET /api/health` | Server health |
| `POST /api/upload` | Multipart form upload with a `file` PDF field, up to 25 MB |
| `GET /api/papers` | List stored paper metadata |
| `GET /api/papers/{id}` | Read one paper's metadata |
| `GET /api/papers/{id}?include_text=true` | Read metadata and extracted text |
| `POST /api/papers/{id}/analyze` | Queue model analysis; returns HTTP 202 |
| `POST /api/core/analyze` | Internal loopback endpoint: UTF-8 `text/plain` paper text → structured analysis JSON |

In standalone mode, PDFs without an extractable text layer return HTTP 422.
The full Python app supplies scanned-PDF OCR, literature grounding, discovery,
chat, compare, and exports. The C++ server binds only to `127.0.0.1`; it is a
local capstone component, not an internet-facing deployment server.

Run the focused HTTP tests after building:

```sh
python -m unittest discover -s cpp/tests -v
```

The tests use PyMuPDF (`fitz`) to create sample PDFs and a local fake model
provider; they do not make paid model calls.
